# scenarios 폴더 안내

## 1. 이 폴더가 뭔가

안전점수 엔진이 **반드시 통과해야 하는 계약서**입니다. 폴더 안의 JSON 파일 하나가 "이런 주행 신호가 들어오면 엔진은 이런 결과를 내야 한다"는 약속 하나입니다.

- JUnit 테스트 하나가 이 폴더의 JSON을 전부 읽습니다. 신호를 엔진에 흘려 넣고, 나온 결과를 `expect`와 비교합니다.
- 시나리오를 추가하고 싶으면 **JSON 파일 하나만 추가**하면 됩니다. 테스트 코드는 고치지 않습니다.
- 기준 문서(정본)는 스펙 7-1절입니다. 이 폴더와 스펙이 다르면 스펙이 맞고, 다른 이유는 아래 9절에 적었습니다.

## 2. 파일 형식

최상위 키는 이렇습니다.

| 키 | 설명 |
|---|---|
| `name` | 시나리오 이름(파일 이름과 같음) |
| `spec` | 스펙 7-1절의 몇 번 시나리오인지 |
| `description` | 무엇을 검증하는지 한 줄 |
| `notes` | 스펙 표와 다른 점, 설계 이유. **러너는 무시**합니다. 없을 수도 있음 |
| `config` | (선택) EngineConfig 값을 덮어쓸 때만 있음. 지금은 S14만 사용 |
| `signals` | 시간 순서로 나열한 입력 신호 목록 |
| `tickEveryMs` | 몇 ms마다 `onTick`을 부를지 (전부 1000) |
| `endAt` | 이 시각(ms)까지 틱을 흘리고 끝냄 |
| `distanceKmOverride` | 주행 거리를 이 값(km)으로 가정. `null`이면 엔진이 속도로 직접 계산 |
| `expect` | 기대 결과 (3절) |

`signals` 한 줄은 `t`와 아래 다섯 가지 중 **정확히 하나**를 가집니다.

| 키 | 값 |
|---|---|
| `t` | 시나리오 시작 기준 시각(ms). 항상 필요 |
| `speed` | 속도(m/s). 후진은 음수 |
| `brake` | 브레이크 페달 `true` / `false` |
| `steering` | 조향각(도). 왼쪽이 음수 |
| `turnSignal` | `"OFF"` / `"LEFT"` / `"RIGHT"` |
| `gear` | `"P"` / `"R"` / `"N"` / `"D"` |

규칙: **같은 `t`에 신호가 둘 이상이면 파일에 적힌 순서대로** 처리합니다.

## 3. expect 필드 정의

| 필드 | 의미 |
|---|---|
| `valid` | 인정된 세션인지. `false`면 점수를 비교하지 않음 |
| `events` | 나와야 하는 이벤트 목록(순서대로, 개수까지 같아야 함) |
| `events[].type` | `HARSH_ACCEL`, `HARSH_BRAKE`, `LANE_CHANGE_NO_SIGNAL` 등 |
| `events[].severity` | 심각도 1 또는 2 |
| `events[].fromStop` | **HARSH_ACCEL에만** 있음. 정차에서 출발한 급가속이면 `true` |
| `scoreByMode` | 심각도 후보별 최종 점수 `{ "b", "a", "c" }`. `valid=false`면 `null` |
| `feedbackCues` | 음성 안내(cue) 횟수를 타입별로. 예: `{ "HARSH_BRAKE": 2 }`. SESSION_START cue는 세지 않음 |
| `firstCueAtMs` | 첫 cue 시각 범위 `{ "min", "max" }` (ms) |
| `validatedAtMs` | "인정됨" 신호가 나온 시각 범위 `{ "min", "max" }` (ms) |
| `eventsBeforeValidated` | 인정되기 전에 이미 방출된 이벤트 수 |

비교할 때 주의할 점:

- 심각도 후보 **(a)** 에서는 엔진이 severity를 항상 1로 냅니다. 그래서 러너는 (a) 모드일 때 **severity 비교를 건너뜁니다**. (b), (c)에서는 비교합니다.
- 차선변경 계열의 severity는 항상 1입니다.
- `valid=false`면 점수 비교는 하지 않습니다.
- `*AtMs` 값은 정확히 같은지 보지 않고 **min/max 범위 안인지**만 봅니다.

## 8. 러너(FakeScenarioSource) 만들 때 알아야 할 것

- **가상 시계**: 시계는 JSON의 `t`입니다. 시스템 시계(`System.currentTimeMillis` 등)는 쓰지 않습니다.
- **신호와 틱의 순서**: `signals`를 `t` 순으로 흘리고, `tickEveryMs`마다 `onTick(t)`를 부릅니다. 신호와 틱이 같은 `t`면 **신호를 먼저, 틱을 나중에** 부릅니다.
- **정차 3분 종료**: 마지막 신호 뒤에는 `endAt`까지 틱만 흘려서, 정차 3분 자동 종료가 일어나게 합니다.
- **세션 시작 전 신호도 넣기**: 세션이 시작되기 전에 들어온 신호도 리샘플러와 버퍼에 넣어야 합니다. 출발 직후 이벤트의 1초 구간이 시작 전 샘플을 포함하기 때문입니다.
- **정속 구간의 하트비트**: 일정 속도로 달리는 구간에도 1초마다 같은 `speed`를 넣었습니다. 스펙 2절대로 속도는 주기 구독이라 실차에서도 정속 중에 콜백이 계속 옵니다. 이것을 흉내 낸 것이고, 없으면 2-2의 stale 규칙에 걸립니다.
- **정차 구간**: 정차 중에는 `speed` 0을 한 번만 넣습니다. 스펙 2-2에서 정차는 stale로 보지 않기 때문입니다.
- **거리 주입**: `distanceKmOverride`가 있으면, 러너가 첫 신호 시각에 `TripDistance(0 m)`, 마지막 신호 시각에 `TripDistance(값 x 1000 m)`를 주입합니다. (스펙 7-1과 같습니다.) `null`이면 주입하지 않고 엔진이 속도를 적분한 거리를 씁니다.
- **override를 무시해도 점수는 같음**: 10km 가정 시나리오는 모두 속도 적분 거리도 1~10 km 사이입니다. 그래서 override를 무시해도 거리 정규화 D=10이 되어 같은 점수가 나옵니다.
- **config 덮어쓰기**: `config`가 있으면 EngineConfig의 해당 값만 덮어씁니다(예: `F_same_s`). 없으면 테스트 기본값을 씁니다.
- **이동평균은 후행(trailing)**: 현재 값과 직전 2개를 평균 냅니다(스펙 2-1).
- **fromStop 판정 기준**: 이벤트가 시작된 1초 구간의 시작 속도 `v(t_start − 1.0s) < 1.0 m/s`이면 `fromStop=true`입니다(스펙 4-1). 이벤트 시작 순간의 속도는 이미 가속 중이라 1.0을 넘기 때문에 구간 시작 속도로 봅니다.
- **반올림**: 점수는 round_half_up입니다(.5는 올림). S3·S11·S15의 (b) 점수는 92.5 → 93, 76.5 → 77, 86.5 → 87로 정확히 .5에 걸리므로 Kotlin의 `Math.round`나 `roundToInt`(둘 다 .5를 올림)는 통과하지만, 은행가 반올림(`RoundingMode.HALF_EVEN`)을 쓰면 92·76·86이 나와 실패합니다.
- **시각 비교**: 이벤트 판정 시각 같은 `*AtMs` 값은 `min`/`max` 범위 안에 들어오는지로 비교합니다.

## 9. 스펙 표보다 더 정한 것

- **S13**: 신호가 끊긴 구간에 브레이크 페달이 눌려 있는 상태를 추가했습니다. stale 제외 규칙이 없으면 재개 시점의 속도 계단(-5.56 m/s²)이 급제동으로 잘못 잡히는지를 확인하기 위해서입니다.

- **모든 유효 시나리오**: 최소 유효 세션 조건(3분)을 채우려고 200초 정속 구간을 넣었습니다(스펙 7-1).
